## 9. To fix between the two arms

`run_pil_campaign.py`'s per-run summary line uses a bare `print()`. Python
block-buffers stdout when it is redirected to a file, and `os.execv` replaces
the process image without flushing, so that line is discarded on every
re-exec: the log shows progress percentages and no results. The JSON is
written with `write_text`, which closes the file, so **no measurement is
affected** — this is a logging defect only. `flush=True` fixes it. It is not
being applied while the actor arm is running, because each re-exec reloads the
file from disk and a syntax error would end a three-hour run; it goes in
between the arms.

## 10. A mis-specified scenario axis, recorded not repaired

**`comm_delay` does not measure what its name and my comment claim.**

Measured, actor arm: `none` (0 ms) gives tracking RMSE 0.0256 m/s and 8 stale
steps. `one_period` (10 ms) gives **32.84 m/s and 13,157 stale steps** — the
loop has effectively collapsed. `ctrl_late` is 0 in both, so the board met
every one of its own deadlines.

The reasoning in `src/evpil/control/scenarios.py` says 10 ms is "one control
period, so the board acts on a state one step old". That is wrong. The delay is
a `sleep` before every reply and it serialises with the host's own plant step,
so at a 10 ms delay on a 10 ms loop the host can no longer service a 100 Hz
request stream at all. It does not fall one step behind, it falls behind
without bound.

So the axis measures **host throughput**, not link latency. A real latency test
would delay delivery without reducing throughput, which needs a queue the
harness does not have.

**Not repaired, deliberately.** GOAL.md fixes the six axes and their three
levels, and redesigning an axis after seeing its result is exactly the move the
protocol exists to prevent. The runs are recorded as measured and the report
states what they do and do not show. The finding is real and worth having: the
PIL rig has no host-side latency budget, because the host is already running at
the loop period.

For the morning: if the intent was to characterise link latency, this axis
needs rebuilding around a delivery queue and re-running. The other five axes are
unaffected.

## 11. THE FINDING THAT MAY CHANGE THE PAPER — read this first

**On US06 the learned controller uses 7.5 per cent LESS energy than the rule
manager, and the project's standing claim is that it uses 0.51 per cent more.**

Measured, one run per arm so far:

| Cycle | Peak current | Rule, Wh/km | Actor, Wh/km | Actor vs rule |
|---|---|---|---|---|
| HWFET highway | 104 A | 154.01 | 154.14 | +0.09% |
| UDDS urban | 118 A | 168.11 | 168.56 | +0.27% |
| US06 aggressive | 284 A | 190.79 | 176.53 | **-7.47%** |

Both on the comparable scale, shed cabin heat charged back. Same distance to
three decimals, both arms, so this is not a tracking artefact: the actor's
tracking is *better* on all three (US06 max error 0.156 m/s against 0.184).

**The mechanism looks real.** The actor's peak current is lower on every cycle
(268.3 A against 284.3 A on US06) because it sets a discharge power ceiling and
the rule manager effectively does not. Peak current is where I2R loss lives, so
the saving scales with how aggressive the cycle is, which is exactly the
ordering above. Ablation A4 saw the same thing from the other side and recorded
it as "consistent with the actor's power limit" because `p_limit_w` is not
logged. It still is not logged, so this remains a mechanism that fits rather
than one that is proven.

**Why this does not contradict week 8.** The 154.68-against-153.90 figure the
report quotes is at the highway scale, and the highway row above reproduces it
almost exactly (154.14 against 154.01). Week 8 measured where the effect is
absent. It was not wrong; it was narrow.
