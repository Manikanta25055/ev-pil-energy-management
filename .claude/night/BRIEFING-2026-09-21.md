### Two self-inflicted failures, both fixed, recorded because they cost board time

1. `reset_and_reexec` re-execs the process, and the first version called it once
   per run inside a loop — which would have restarted the campaign from run 1
   every time. It failed immediately on an unrecognised `--no-reset`, so nothing
   was measured wrongly. The script now runs one cell per process and resumes
   from the file it has already written.
2. `SerialLink.stats` is a `@property`; the script read it as `link.stats()`.
   That threw at the *end* of the actor arm's first run and discarded 23 minutes
   of board time. `run_g3.py` had it right and this script did not. The read has
   moved into `run_one`, which the fake-link tests exercise, and `FakeBoard` now
   exposes `stats` as a property so the regression test fails the way the board
   did. **No measurement was recorded from either failure, so no configuration
   has been run twice.**

After the second one, `--max-steps` was added and the whole `main()` path was
smoke-tested against the board before the three-hour arm was started again.

## 9. To fix between the two arms

`run_pil_campaign.py`'s per-run summary line uses a bare `print()`. Python
block-buffers stdout when it is redirected to a file, and `os.execv` replaces
the process image without flushing, so that line is discarded on every
re-exec: the log shows progress percentages and no results. The JSON is
written with `write_text`, which closes the file, so **no measurement is
affected** — this is a logging defect only. `flush=True` fixes it. It is not
being applied while the actor arm is running, because each re-exec reloads the
file from disk and a syntax error would end a three-hour run; it goes in
between the arms.
